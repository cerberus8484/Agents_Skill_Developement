CCD-Wertesystem

skills/ccd-wertesystem/SKILL.md

This skill MUST be activated when evaluating code quality, doing code reviews, grading code, discussing refactoring priorities, or when the user mentions "CCD", "Wertesystem", "Grade", "Schwarz", "Weiß", "Rot", "Orange", "Gelb", "Grün",…

CCD Wertesystem — Clean Code Developer

Das CCD-Wertesystem ist ein graduelles Entwicklungsmodell. Ziel ist nicht sofortiger Weiß-Grad — sondern bewusste, schrittweise Verbesserung. Jeder Grad baut auf dem vorherigen auf.

Die 4 Grundwerte

Diese Werte sind die Basis — ohne sie sind alle Praktiken wertlos.

Grundwert Bedeutung im Code
Ehrlichkeit Code sagt die Wahrheit. Namen lügen nicht. Kommentare sind aktuell. Fehler werden nicht versteckt.
Sorgfalt Jede Zeile mit Bedacht. Kein "wird schon funktionieren". Kein "refaktor ich später".
Mut Schlechten Code refactoren auch wenn es schwierig ist. Technische Schulden benennen. Nein sagen zu Abkürzungen.
Verantwortung Der Code ist dein Handwerk. Du stehst dafür ein. Qualität ist keine Option.

Die 10 Tugenden

# Tugend Konkret
1 Mühelosigkeit Code liest sich wie Prosa. Kein mentaler Kampf beim Verstehen.
2 Einfachheit Die einfachste Lösung die funktioniert. Keine over-engineered Abstraktion.
3 Klarheit Intent sofort erkennbar. Kein "was macht das nochmal?".
4 Wandelbarkeit Änderungen sind sicher und vorhersehbar. Kein "ich traue mich nicht".
5 Korrektheit Macht was es soll — immer, nicht meistens. Edge Cases behandelt.
6 Wirtschaftlichkeit Kein überflüssiger Code. Kein Gold-Plating. Kein Dead Code.
7 Vertrauen Entwickler vertrauen dem Code. Keine Angst vor dem System.
8 Sichere Basis Tests geben Sicherheit für jede Änderung. Kein Blindflug.
9 Emergente Struktur Struktur entsteht aus Anforderungen — nicht aus Vorstellung.
10 Professionalität Code als Handwerk. Craft over Career.

Die 7 Grade

⬛ Grad 7 — Schwarz (Ausgangspunkt)

Charakteristik: Funktioniert irgendwie. Niemand versteht warum.

- Keine Struktur erkennbar
- Alles in einer Datei / einer Funktion
- Magic Numbers überall
- Kein Fehler-Handling
- Keine Tests
- Copy-Paste-Code in großen Mengen
- Namen: a, b, x, temp, data2

Bewertungs-Indikator: Neuer Entwickler braucht Tage um zu verstehen was eine Funktion macht.

🟫 Grad 6 — Braun

Charakteristik: Grundlegende Strukturierung vorhanden. Aber Prinzipien fehlen.

Praktiken die einzuhalten sind: - Funktionen vorhanden (keine God-Functions) - Sinnvolle Dateinamen - Keine offensichtlichen Magic Numbers - Grundlegendes Fehler-Handling

Noch nicht vorhanden: - DRY (viel Duplikation) - Kein einheitlicher Stil - Keine Tests

🔴 Grad 5 — Rot

Charakteristik: Entwickler hat Clean Code gehört aber nicht verinnerlicht.

Praktiken: - ✅ Sinnvolle Variablen- und Funktionsnamen - ✅ Keine Magic Numbers (Konstanten) - ✅ Grundlegendes DRY (keine offensichtliche Duplikation) - ✅ Fehler werden nicht stillschweigend ignoriert

Verletzungen die hier enden: - ❌ SRP: Funktionen machen noch mehrere Dinge - ❌ Keine Tests oder nur Pseudo-Tests - ❌ Kommentare erklären WAS, nicht WARUM

Bewertungs-Indikator: Code ist lesbar aber noch nicht wartbar.

🟠 Grad 4 — Orange

Charakteristik: Solide Grundlagen. Einzelne Prinzipien konsequent eingehalten.

Praktiken (alle aus Rot + zusätzlich): - ✅ SRP: jede Funktion eine Verantwortung - ✅ DRY konsequent: keine Duplikation - ✅ KISS: keine unnötige Komplexität - ✅ Erste Tests vorhanden - ✅ Kommentare erklären WARUM

Noch ausbaufähig: - ⚠️ Tests nicht systematisch (lückenhaft) - ⚠️ OCP / DIP noch nicht konsequent - ⚠️ Interfaces noch zu groß

Bewertungs-Indikator: Neue Features können hinzugefügt werden ohne Angst.

🟡 Grad 5 — Gelb (korrigiert: Grad 3)

Charakteristik: Meiste Prinzipien eingehalten. Code macht Freude.

Praktiken (alle aus Orange + zusätzlich): - ✅ SOLID vollständig eingehalten - ✅ Dependency Injection konsequent - ✅ Kleine, fokussierte Interfaces - ✅ Tests mit guter Coverage (Happy + Error + Edge) - ✅ CQS: Query/Command getrennt - ✅ IOSP: Integration/Operation getrennt - ✅ LoD eingehalten

Bewertungs-Indikator: Refactoring ist sicher. CI gibt Vertrauen.

🟢 Grad 2 — Grün (Ziel-Standard)

Charakteristik: Alle Kernprinzipien eingehalten. Professioneller Code.

Praktiken (alle aus Gelb + zusätzlich): - ✅ TDD oder Test-First-Mentalität - ✅ SLA: eine Abstraktionsebene pro Funktion - ✅ FCoI: Komposition statt Vererbung - ✅ PoLA: keine Überraschungen - ✅ Kein Dead Code, kein auskommentierter Code - ✅ Alle Abhängigkeiten explizit (keine globalen States) - ✅ Dokumentation wo wirklich nötig (Warum, nicht Was) - ✅ Emergente Architektur — nichts over-engineered

Bewertungs-Indikator: Jeder Entwickler kann jeden Teil des Codes sofort verstehen und ändern.

⬜ Grad 1 — Weiß (Exzellenz)

Charakteristik: Mustergültig. Code als Lehrbeispiel.

Praktiken (alle aus Grün + zusätzlich): - ✅ Continuous Refactoring (Boy Scout Rule: hinterlasse es besser als du es gefunden hast) - ✅ Evolutionäre Architektur - ✅ Technische Schulden werden sofort beglichen - ✅ Code kommuniziert Intent auf allen Ebenen - ✅ Kein Kommentar nötig — Code erklärt sich selbst - ✅ Jede Abhängigkeit bewusst und dokumentiert - ✅ Metriken werden beobachtet und reagiert

Bewertungs-Indikator: Der Code ist wartbarer als alles was man bisher gesehen hat.

Code-Review mit CCD-Wertesystem

Grading-Prozess

1. Lese den Code ohne ihn auszuführen
2. Welche Prinzipien sind verletzt? → bestimmt Mindestgrad
3. Welche Praktiken sind eingehalten? → bestimmt maximalen Grad
4. Wo auf der Skala liegt der Code? → Grad festlegen
5. Was ist der nächste konkrete Schritt zur Verbesserung?

Typische Grade in der Praxis

Grad 6-5 (Braun-Rot):  Legacy-Code, Hack-Sessions, "es musste schnell gehen"
Grad 4   (Orange):     Durchschnittlicher Produktionscode
Grad 3   (Gelb):       Bewusst geschriebener, gepflegter Code
Grad 2   (Grün):       Ziel für jedes professionelle Projekt
Grad 1   (Weiß):       Selten — aber der Maßstab

Praktische Bewertungs-Schnellchecks

30-Sekunden-Check (Grad 5 oder schlechter?)

- Gibt es Funktionen > 20 Zeilen?          → Rot oder schlechter
- Gibt es Kommentare die WAS erklären?     → Orange oder schlechter
- Gibt es Magic Numbers?                   → Rot oder schlechter
- Gibt es copy-paste Code?                 → Braun oder schlechter
- Sind Namen kryptisch?                    → Schwarz oder schlechter

5-Minuten-Check (Grad 3 oder besser?)

- Kann ich jede Funktion in einem Satz beschreiben?  → SRP eingehalten
- Kann ich eine Abhängigkeit austauschen?             → DIP eingehalten
- Haben alle Funktionen Tests?                        → Sichere Basis
- Gibt es Überraschungen beim Lesen?                  → PoLA eingehalten
- Sind alle Pfade abgedeckt (Happy + Error)?          → Korrektheit

Clean Code

skills/clean-code/SKILL.md

This skill MUST be activated for every coding session — when writing new code, reviewing existing code, refactoring, writing tests, or making architecture decisions. Activates on any task involving Go, TypeScript, Python, SQL, shell…

Clean Code Skill — Professional Development Standards

PFLICHT: Dieser Skill ist bei JEDER Coding-Session aktiv. Kein Code ohne diese Standards — das ist nicht optional.

CCD Wertesystem — 7 Grade

Grad Farbe Bedeutung
7 ⬛ Schwarz Unverständlich, nicht wartbar
6 🟫 Braun Funktioniert, aber schlecht strukturiert
5 🔴 Rot Grundlegende Prinzipien verletzt
4 🟠 Orange Manche Prinzipien eingehalten
3 🟡 Gelb Meiste Prinzipien eingehalten
2 🟢 Grün Alle Kernprinzipien eingehalten
1 ⬜ Weiß Exzellenter, mustergültiger Code

Ziel: Grün (2) als Standard. Weiß (1) als Ambition.

SOLID-Prinzipien

S — Single Responsibility Principle

  • Eine Klasse/Funktion hat genau eine Verantwortung
  • Wenn du "und" brauchst um eine Funktion zu beschreiben → aufteilen
  • Max. ~20 Zeilen pro Funktion als Faustregel

O — Open/Closed Principle

  • Offen für Erweiterung, geschlossen für Modifikation
  • Verhalten über Interfaces/Komposition erweitern, nicht durch if-Ketten
  • Neue Features → neuer Code, nicht alter Code verändert

L — Liskov Substitution Principle

  • Subtypen müssen Supertypen ersetzen können ohne Überraschungen
  • Interfaces: alle Methoden müssen sinnvoll implementierbar sein
  • Keine "NotImplementedException" in Implementierungen

I — Interface Segregation Principle

  • Kleine, fokussierte Interfaces statt fetter Monolith-Interfaces
  • Client soll nicht von Methoden abhängen, die er nicht nutzt
  • Go: kleine Interfaces (1-3 Methoden) bevorzugen

D — Dependency Inversion Principle

  • High-level Module hängen nicht von Low-level Modulen ab
  • Beide hängen von Abstraktionen (Interfaces) ab
  • Abhängigkeiten von außen injizieren (Constructor Injection)

OOP & Clean Code Prinzipien

DRY — Don't Repeat Yourself

  • Jede Information hat genau eine autoritative Quelle
  • Duplikation ist die Wurzel aller Wartungsprobleme
  • Aber: Falsche Abstraktion ist schlimmer als Duplikation — YAGNI beachten

KISS — Keep It Simple, Stupid

  • Die einfachste Lösung ist fast immer die beste
  • Komplexität rechtfertigen müssen — nicht Einfachheit
  • "Perfection is achieved not when there's nothing more to add, but when there's nothing left to remove"

YAGNI — You Ain't Gonna Need It

  • Keine Features für hypothetische zukünftige Anforderungen bauen
  • Jede Zeile Code ist eine Wartungslast
  • Erst wenn der Bedarf real ist → implementieren

IOSP — Integration Operation Segregation Principle

  • Funktionen entweder integrieren (andere aufrufen) ODER operieren (Logik ausführen)
  • Nicht beides gemischt
  • Macht Unit-Tests trivial

LoD — Law of Demeter

  • Sprich nur mit direkten Nachbarn
  • a.b.c.doSomething() → Verletzung
  • Jede Klasse kennt nur ihre unmittelbaren Abhängigkeiten

SoC — Separation of Concerns

  • Verschiedene Belange in verschiedene Module/Schichten
  • HTTP-Handler kennt keine DB-Details
  • Business-Logik kennt kein HTTP

CQS — Command Query Separation

  • Funktionen entweder Daten lesen (Query) ODER verändern (Command)
  • Nie beides
  • GetUser() verändert nichts. DeleteUser() gibt nichts zurück.

PoLA — Principle of Least Astonishment

  • Code soll sich so verhalten wie der Leser erwartet
  • Keine Überraschungen, keine versteckten Nebenwirkungen
  • Namen müssen ehrlich sein

SLA — Single Level of Abstraction

  • Innerhalb einer Funktion nur eine Abstraktionsebene
  • Nicht: SQL-Query + Business-Logik + HTTP-Response in einer Funktion

FCoI — Favour Composition over Inheritance

  • Komposition flexibler und testbarer als Vererbung
  • Go hat keine Vererbung — das ist ein Feature, kein Bug

10 CCD Tugenden

  1. Mühelosigkeit — Code liest sich wie Prosa, kein Kampf
  2. Einfachheit — die einfachste Lösung wählen
  3. Klarheit — Intent sofort erkennbar
  4. Wandelbarkeit — leicht zu ändern ohne Angst
  5. Korrektheit — macht was es soll, immer
  6. Wirtschaftlichkeit — kein überflüssiger Code
  7. Vertrauen — Entwickler vertrauen dem Code
  8. Sichere Basis — Tests geben Sicherheit für Änderungen
  9. Emergente Struktur — Struktur entsteht aus den Anforderungen
  10. Professionalität — Code als Handwerk, nicht als Hack

4 CCD Grundwerte

  1. Ehrlichkeit — Code sagt die Wahrheit (Namen, Kommentare)
  2. Sorgfalt — jede Zeile mit Bedacht geschrieben
  3. Mut — schlechten Code refactoren, auch wenn es schwierig ist
  4. Verantwortung — der Code ist dein Handwerk

Checkliste vor jedem Commit

  • [ ] Macht jede Funktion genau eine Sache?
  • [ ] Sind alle Namen ehrlich und selbsterklärend?
  • [ ] Gibt es Duplikation die entfernt werden sollte?
  • [ ] Werden alle Fehler explizit behandelt?
  • [ ] Gibt es Tests für das neue/geänderte Verhalten?
  • [ ] Ist der Code so einfach wie möglich (KISS)?
  • [ ] Keine unnötige Komplexität (YAGNI)?
  • [ ] Kein Code der auf zukünftige Features "vorbereitet"?

Security

skills/security/SKILL.md

This skill MUST be activated when writing or reviewing any security-relevant code — authentication, authorization, session management, token handling, password hashing, API endpoints, middleware, input validation, database queries,…

Security Skill — Professional Security Standards

PFLICHT: Jede sicherheitsrelevante Funktion braucht: Tests · Audit-Log-Verhalten · Secret-Leak-Prüfung · Threat-Model-Update · Privacy-Check

Sicherheits-Grundregeln (absolut, keine Ausnahmen)

1. Secrets gehören NIEMALS in Logs, Code, Git oder Response-Bodies
2. Passwörter werden IMMER gehasht (bcrypt, argon2) — niemals plaintext
3. Tokens werden IMMER gehasht (SHA-256) in der DB — niemals plaintext
4. SQL-Queries IMMER parametrisiert — niemals string-konkateniert
5. User-Input IMMER validieren BEVOR er verarbeitet wird
6. Fehler NIEMALS mit Stack-Traces an den Client — nur intern loggen
7. IPs im Audit-Log IMMER hashen (SHA-256) — kein PII in Klartext
8. TLS in Produktion IMMER — niemals HTTP ohne explizite Dev-Markierung

OWASP Top 10 — Checkliste

A01: Broken Access Control

  • [ ] Jede Route hat explizite Auth-Prüfung
  • [ ] Agent-Routen und Admin-Routen strikt getrennt
  • [ ] Ressourcen-Ownership wird geprüft (kein IDOR)
  • [ ] RBAC-Rollen vor Zugriff validieren

A02: Cryptographic Failures

  • [ ] bcrypt (Cost ≥ 12) für Passwörter
  • [ ] SHA-256 für Token-Hashes
  • [ ] AES-256 für Backup-Verschlüsselung (Restic)
  • [ ] TLS 1.2+ für alle Netzwerkverbindungen
  • [ ] Keine schwachen Algorithmen (MD5, SHA1, DES)

A03: Injection

  • [ ] Ausschließlich parametrisierte Queries (pgx Prepared Statements)
  • [ ] Keine string-konkatenierte SQL
  • [ ] Input-Validierung an allen Trust-Boundaries
  • [ ] Pfad-Traversal-Schutz bei File-Operationen

A04: Insecure Design

  • [ ] Threat Model vor Implementation
  • [ ] STRIDE-Analyse für neue Features
  • [ ] Privacy by Design (Art. 25 DSGVO)
  • [ ] Fail-Secure (bei Fehler → Zugriff verweigert, nicht gewährt)

A05: Security Misconfiguration

  • [ ] Keine Default-Credentials in Produktion
  • [ ] Debug-Mode ausgeschaltet
  • [ ] Fehler-Messages ohne Stack-Traces an Client
  • [ ] Security-Header gesetzt (CSP, HSTS, X-Frame-Options)
  • [ ] CORS restriktiv konfiguriert

A06: Vulnerable Components

  • [ ] go mod audit / npm audit vor Release
  • [ ] Dependencies minimal halten
  • [ ] Keine bekannten CVEs in direkten Dependencies

A07: Authentication Failures

  • [ ] Brute-Force-Schutz (Rate-Limiting)
  • [ ] Session-Invalidierung bei Logout
  • [ ] Session-TTL (max. 8h für Admin)
  • [ ] HttpOnly + SameSite=Strict für Session-Cookies
  • [ ] CSRF-Schutz für alle mutierenden Requests

A08: Software Integrity Failures

  • [ ] Go-Module mit go.sum verifiziert
  • [ ] Keine unkontrollierten Remote-Skript-Ausführungen
  • [ ] Build-Pipeline nicht manipulierbar

A09: Logging Failures

  • [ ] Alle Auth-Events im Audit-Log
  • [ ] Keine Secrets in Logs
  • [ ] Audit-Log append-only (RLS)
  • [ ] IPs gehasht (SHA-256)

A10: SSRF

  • [ ] Keine unkontrollierten HTTP-Requests zu User-supplied URLs
  • [ ] Whitelist für erlaubte externe URLs

Security-Code-Review-Checkliste

Vor jedem sicherheitsrelevanten Merge:

Auth & Session: - [ ] Passwort-Hash mit bcrypt (Cost ≥ 12)? - [ ] Session-Token kryptografisch zufällig (32+ Bytes)? - [ ] Cookie: HttpOnly=true, SameSite=Strict, Secure (bei TLS)? - [ ] Session server-seitig invalidierbar? - [ ] CSRF-Token bei mutierenden Requests?

Tokens: - [ ] Token nur als SHA-256-Hash in DB? - [ ] Token nie in Logs, Responses oder Errors? - [ ] Einmal-Tokens wirklich invalidiert nach Verwendung? - [ ] TTL gesetzt und durchgesetzt?

Input: - [ ] Alle User-Inputs validiert? - [ ] Body-Size limitiert (MaxBytesReader)? - [ ] Pfad-Traversal ausgeschlossen? - [ ] UUID-Parsing mit uuid.Parse() (nicht string-compare)?

Datenbank: - [ ] Alle Queries parametrisiert? - [ ] Kein fmt.Sprintf in SQL? - [ ] Migrations idempotent?

Logging: - [ ] Kein env.RESTIC_PASSWORD, ADMIN_PASSWORD, token in Logs? - [ ] IP gehasht (security.ClientIPHashed)? - [ ] Details-Feld im Audit-Log enthält kein PII?

DSGVO

skills/dsgvo/SKILL.md

This skill MUST be activated when writing code that processes personal data, handles user data, implements deletion or export functions, touches audit logging, deals with data retention, implements consent mechanisms, or when the user…

DSGVO/GDPR Skill — Datenschutz by Design

Wichtige Einordnung: Code kann technische Bausteine für DSGVO-konformen Betrieb implementieren. DSGVO-Konformität als Gesamtzustand entsteht durch: Rechtsgrundlage + TOMs + Prozesse + Dokumentation + Betriebskonzept — nicht allein durch Code.

Privacy by Design — Art. 25 DSGVO

Beim Schreiben von Code IMMER prüfen:

1. Datenminimierung: Brauchen wir dieses Datum wirklich?
2. Zweckbindung: Wird es nur für den dokumentierten Zweck genutzt?
3. Speicherbegrenzung: Gibt es eine Retention-Policy?
4. Pseudonymisierung: Kann PII durch Pseudonyme ersetzt werden?
5. Default-Privacy: Restriktivste Einstellung als Standard

Personenbezogene Daten — Erkennungsmuster

Im Code als PII zu behandeln:

  • IP-Adressen (auch IPv6) → IMMER hashen vor Speicherung
  • E-Mail-Adressen
  • Namen, Vornamen, Benutzernamen
  • Hostnamen wenn personenbeziehbar
  • Dateipfade die auf Personen hinweisen
  • Geräte-IDs, Session-IDs wenn persistiert
  • Backup-Inhalte (können beliebige PII enthalten)

Technische Identifikatoren (kein direktes PII):

  • UUIDs (pseudonym, aber korrelierbar)
  • SHA-256-Hashes von IPs
  • System-IDs im OpenSourceBackup-Kontext

Betroffenenrechte — Code-Umsetzung

Art. 15 — Auskunftsrecht

// Implementierung: Export-Endpunkt
GET /v1/gdpr/systems/{id}/export
// Liefert: alle Metadaten, Jobs, Snapshots, Audit-Einträge
// NICHT: Backup-Inhalte (liegen im Restic-Repository)

Art. 17 — Recht auf Löschung

// Implementierung: Purge-Endpunkt
DELETE /v1/gdpr/systems/{id}/purge
// Löscht: Katalogdaten kaskadierend
// NICHT automatisch: Backup-Inhalte im Repository
// → Manueller Prozess: restic forget --prune + Dokumentation
// WORM-Ausnahme dokumentieren wenn Object-Lock aktiv

Art. 20 — Datenportabilität

// Implementierung: Export als JSON
GET /v1/gdpr/systems/{id}/export
// Format: maschinenlesbar, strukturiert, vollständig

Art. 17 Abs. 3 — Ausnahmen von der Löschpflicht

  • Gesetzliche Aufbewahrungspflichten (z.B. GoBD, Steuerrecht)
  • Geltendmachung von Rechtsansprüchen
  • WORM/Object-Lock-Retention → In Datenschutzkonzept dokumentieren, nicht im Code verstecken

Audit-Log — DSGVO-Anforderungen

Was MUSS geloggt werden:

  • Alle GDPR-Aktionen (Export, Purge) — VOR Ausführung
  • Alle Auth-Events (Login, LoginFail, Logout)
  • Alle Datenlöschungen

Was DARF NICHT geloggt werden:

  • Passwörter (auch gehasht gehören nicht in den Audit-Log)
  • Tokens (weder Klartext noch Hash)
  • Backup-Inhalte
  • Authorization-Header
  • RESTIC_PASSWORD, ADMIN_PASSWORD
  • Vollständige Request-Bodies

IP-Behandlung:

// FALSCH:
audit.Entry{IP: security.ClientIP(r)}  // Klartext-PII

// RICHTIG:
audit.Entry{IP: security.ClientIPHashed(r)}  // SHA-256-Hash

Datenminimierung — Checkliste

Vor jeder neuen DB-Spalte oder neuen gespeicherten Daten:

  • [ ] Wird dieses Datum für den dokumentierten Zweck benötigt?
  • [ ] Kann es pseudonymisiert werden?
  • [ ] Gibt es eine Retention-Policy?
  • [ ] Ist es im Verarbeitungsverzeichnis dokumentiert?
  • [ ] Fällt es unter eine Rechtsgrundlage (Art. 6)?

Art. 6 Abs. 1 lit. f Berechtigtes Interesse IT-Sicherheit, Audit-Log
Art. 6 Abs. 1 lit. a Einwilligung Wenn keine andere Grundlage

Wichtig: Rechtsgrundlage muss VOR der Verarbeitung feststehen und dokumentiert sein. Das ist Betreiber-Aufgabe, nicht Code-Aufgabe.

Privacy-Check — vor jedem Feature-Merge

□ Verarbeitet dieses Feature personenbezogene Daten?
  → Ja: Zweck dokumentiert? Rechtsgrundlage klar?

□ Werden neue Daten in DB gespeichert?
  → Ja: Retention-Policy? Pseudonymisierung möglich?

□ Werden Daten an externe Systeme gesendet?
  → Ja: Auftragsverarbeitungsvertrag (AVV) vorhanden?

□ Gibt es neue Logging-Statements?
  → Ja: Enthält kein PII (Name, IP, E-Mail, Pfade mit Personenbezug)?

□ Gibt es neue Fehler-Responses?
  → Ja: Enthält keine internen Daten, Stack-Traces, IDs die PII sind?

□ Betrifft es Backup-Inhalte?
  → Ja: Löschprozess für Restic-Repository dokumentiert?

Verarbeitungsverzeichnis — Art. 30 DSGVO

Betreiber-Pflicht (nicht im Code, aber im Deployment-Prozess):

Verarbeitungstätigkeit: Datensicherung
Verantwortlicher: [Betreiber]
Zweck: IT-Betriebskontinuität, Datenverfügbarkeit
Kategorien Betroffener: Mitarbeiter, ggf. Kunden
Datenkategorien: Dateien, Datenbanken (systemabhängig)
Empfänger: [Cloud-Provider bei S3/Azure]
Drittlandtransfer: [Nein/Ja + Grundlage]
Löschfristen: Snapshots [X] Tage, Katalog [Y] Tage
TOMs: siehe docs/security/tom.md

❌ Falsch ✅ Richtig

Verknüpfung mit Security-Skill

DSGVO und Security sind untrennbar.

Art. 32 DSGVO verlangt "geeignete technische und organisatorische Maßnahmen" — das ist exakt was der Security-Skill sicherstellt.

Beide Skills sind immer zusammen aktiv wenn: - Personenbezogene Daten verarbeitet werden - Auth-Code geschrieben wird - Audit-Log befüllt wird - Lösch- oder Export-Funktionen implementiert werden

→ Referenz: docs/security/tom.md enthält die vollständige TOM-Tabelle mit dem Mapping zwischen Security-Maßnahmen und DSGVO-Artikeln
